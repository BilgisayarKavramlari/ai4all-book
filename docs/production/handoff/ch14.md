| Term | Definition | Türkçe |
|---|---|---|
| Workflow | A fixed sequence of steps for a task, run by people, by software or by both. | İş akışı |
| Automated workflow | A workflow whose steps software runs, along a path people fixed in advance. | Otomatik iş akışı |
| Agent loop | The cycle an agent repeats: the model produces a plan for the next action, the system runs the tool call, and the result, the observation, is added to the context window, until a stop condition is met. | Ajan döngüsü |
| Error compounding | The tendency for the chance of an error-free run to fall as steps are added, because each step is another chance for an error and later steps can build on earlier ones. | Hata birikmesi |
| Reversible action | An action whose effect can be undone at little cost, such as a draft, an item in a cart or a change in a test copy. | Geri alınabilir eylem |
| Approval gate | A point at which a system pauses before an action takes effect until a named person approves, edits or rejects it. | Onay kapısı |
| Check point | A point at which a person inspects an intermediate result before later steps build on it (not a saved restore point). | Kontrol noktası |
| Stop point | A condition at which a run halts and hands control back to a person, such as a step, time or spending limit, an error, or an unexpected result. | Durma noktası |
| Soft gate | An instruction in the context asking the model to ask first or not to act; the model receives it as text and may not follow it. | Yumuşak kapı |
| Hard gate | A gate the system enforces outside the model, so the action cannot run unless a person acts, or cannot run at all. | Sert kapı |
| Approval fatigue | Approvals given so often or so quickly that they stop working as checks. | Onay yorgunluğu |
| Least privilege | Giving each tool and account only the access its step needs, for only as long as it is needed. | En az yetki |
| Sandbox | A separate test copy where changes do not reach real data or people. | Korumalı alan (test ortamı) |
| Log (of an agent run) | A record the system writes as it runs of every plan, tool call, observation, approval and stop, with times. | Kayıt (ajan çalışma günlüğü) |
| Dry run | Running a whole workflow on test inputs with real effects switched off, before anyone relies on it. | Kuru çalıştırma (prova) |
| Planted fault | An error put into one step of a dry run on purpose, to see whether a check point, gate or stop point catches it. | Yerleştirilmiş hata |
| Done-criteria | Two or three checks that tell you whether a run succeeded. | Tamamlanma ölçütleri |
| Workflow blueprint | A written design of a workflow: its steps, who or what runs each, its actions, people points, permissions, log plan and dry-run results. | İş akışı planı |

## Chapter 14

### Review Questions A
1. **(b)** A system whose model chooses its next steps and tool calls toward a goal. (a) M1: a better chatbot is still a chat assistant; (c) what a system can change is a permissions question (M6); (d) that is agency without an agent.
3. **(d)** The result of a tool call, added to the context window before the next plan. (a) is an approval gate (M4); (b) M5: the model's summary is not an observation or a record; (c) is a stop condition.
5. Less reliable: errors can be correlated, so one misread observation spoils many later steps. More reliable: an error can be harmless, or a later step (or a retry) can catch and fix it.
7. A check point: a person inspects an intermediate result before later steps build on it. A stop point: a condition at which the run halts and hands control back to a person (a limit, an error, an unexpected result). An approval gate differs from both: the system pauses before a specific action takes effect until a named person approves, edits or rejects that action.
9. **(d)** That approving is routine; it does not by itself show careless approvals. (a) M4: routine review may not catch errors; (b) and (c) read more into the number than it shows: most proposed actions may have been fine, and the company used the figure to design a different review method.
11. **(c)** A summary is generated text that can be wrong; the system writes the log as it runs. (a) M5: summaries can be fluent and wrong, not just short; (b) agents do not hide things on purpose: the summary is predicted text; (d) completeness is not the main issue: a summary is a claim to check.
13. No. The rung stays agency: the AI still acts on your behalf later. The gate restores a check before consequential actions take effect (Chapter 5: a design can add such a check without changing the rung).

### Review Questions B
1. Chat tool for wording: chat assistant (staff fix and run each step); it changes nothing by itself. Reminder software: automated workflow (people fixed the steps; software runs them); it sends messages to patients. Cancellation filler: agent (the model chooses whom to contact; software runs the steps); it can send messages, so limit it to drafts or put an approval gate before sending.
3. Soft gate: the instruction "Always ask me before sending anything." Hard gates: remove the agent's permission to send (drafts only), or a confirmation the system enforces before any email leaves. Before approving she must see the recipient, the full message as it will be sent, and the sources with links, and check the sources herself (Chapters 8–9).
5. No account password: draft-only access to the social account through a scheduling tool, with posts approved by staff; no email account (or read-only access to a shared events inbox, if needed); no budget or payment access; stop points (posts outside approved hours, any post mentioning money); a log reviewed weekly.

### Review Questions C
1. Strong answers disagree: approving every action invites approval fatigue (the 93% figure shows approving is routine), and a gate catches only what its approver catches (this book's simulation: a gate cut wrong final actions from 64% to 19%, not to zero). Errors compound, so check points, stop points and least privilege matter too. They grant that approvals of consequential actions are necessary and that a hard gate beats a soft one. Weak answers say "yes" or "approvals are useless."
3. Strong answers disagree: an agent's explanation is text the model produces; in the Opening Case the agent's message said the rollback could not work, and the user later said it did. Evidence comes from a log the system writes and from independent checks. They grant that an explanation can point to where to look. Weak answers treat the apology as a confession or call the agent a liar.

### Spaced Review
1. Chapter 12's data gate: a check, made before any quality test, of whether a tool's data terms fit the class of the input. Members' phone numbers fall in Chapter 12's row 'Personal data about other people (names, contact details), and internal or confidential data': no under consumer terms; under institutional terms only if the part needs it and your institution's rules allow it (ask your institution's IT office if unsure). Otherwise remove the numbers from the input.
3. It triggers an action: an automated decision (Chapter 11). The decision owner is the named person or body who set up the agent and answers for its result, for example the club's treasurer or officers; someone still answers, but only afterward.

### Check Yourself
**14.1** (1) Who fixes the next step, and who runs each step (§14.1 table). (2) Sending is a permission, a question of what a system can change; the kind of system depends on who fixes and runs the next step (§14.1). (3) A fixed workflow is simpler, cheaper and easier to check when the steps are known (§14.1, "Start simple").
**14.2** (1) Goal → plan → (approval gate) → tool call → observation → (check point) → stop? → next pass or hand back (§14.2). (2) Each pass is a new prediction from what the context window holds, so a wrong observation shapes every later plan (§14.2). (3) Between a proposed action and its execution (§14.2, F14.4).
**14.3** (1) The tendency for the chance of an error-free run to fall as steps are added, because each step is another chance for an error and later steps can build on earlier ones (§14.3). (2) All 20 steps must go right: 0.95 multiplied by itself 20 times ≈ 0.36 (§14.3). (3) Worse: correlated errors, one misread observation spoiling later steps. Better: harmless errors, or a later step that catches and fixes one (§14.3).
**14.4** (1) Approval gate: the system pauses before an action until a named person approves, edits or rejects it (e.g., the treasurer before an order). Check point: a person inspects an intermediate result (e.g., the cart lines). Stop point: a condition that halts the run and hands back (e.g., cart over budget) (§14.4). (2) A message to other people cannot be undone and others bear an error; a cart item is reversible and borne by you until the order (§14.4, F14.7). (3) An early error meets several checks, each another chance to catch it, and is fixed before later steps build on it (§14.4).
**14.5** (1) A soft gate is an instruction the model receives and may not follow (e.g., "always ask before ordering"); a hard gate is enforced by the system (e.g., an account that cannot pay) (§14.5). (2) It was an instruction in the context, with nothing in the system enforcing it, and the agent could reach the live data (§14.5). (3) That approving is routine; not that the approvals were careless, since most proposed actions may have been fine (§14.5).
**14.6** (1) Giving each tool and account only the access its step needs, for only as long as needed; can it read, write, send, pay? (§14.6). (2) A separate test copy where changes do not reach real data or people; errors there cost nothing (§14.6). (3) An injected instruction acts with whatever permissions the agent has, so fewer permissions limit what it can do (§14.6).
**14.7** (1) Every plan, tool call, observation, approval and stop, with times; the system writes it as it runs (§14.7). (2) The summary is text the model produces, a claim that can be fluent and wrong, as in the Opening Case's rollback claim (§14.7). (3) Any two: a limit reached; the same failed action repeated; an observation that does not fit; an action outside the plan (§14.7).
**14.8** (1) Running the whole workflow on test inputs with real effects switched off, so a mistake costs nothing before anyone relies on it (§14.8). (2) An error put into one step on purpose to see whether a point catches it, e.g., a page with a hidden instruction (§14.8). (3) Any two: move or add a people point; narrow a permission; use a simpler kind of system; keep a step with a person (§14.8).
