**Author's brief (2026-10-22), restated.** The book never covers *making* something with AI. Chapter 12 is about choosing tools, Chapter 14 about overseeing agents, and section 19.5 builds a no-code prototype in which "nothing sends, publishes, pays or deletes." This chapter teaches six things: how to delegate a build task to an AI tool; what remains yours, and what you must read; how to read code you did not write; the weak spots specific to generated software; what changes when a build goes onto the internet; and where to stop and bring in a professional. Audience: every major, **no programming prerequisite**. It is **not a programming chapter** and must not become a web-development tutorial. It teaches no language and names no framework or platform as the way to build. It has no click paths (those go in Compass). Every code fragment it prints is short, constructed and annotated in plain English. Students read each fragment for *behavior* and never write code. Builds are spread across kinds -- spreadsheet automations, a chatbot over documents, form workflows, file scripts, small sites -- so the chapter is not about web apps only.

**Hard limits (D27, D28, D31).** No institution name, course code, term, schedule, enrollment, grant or funder; generic wording such as "your institution's IT office" or "a tool your institution provides or approves". ASCII letters only in every name (Lucia, Seker). No health-informatics or clinical depth (D31): no clinical build, no patient data, no clinical case, and Marcus does not feature. Tool neutrality: tools are named by kind ("a chat assistant", "a coding agent", "an app builder that generates and hosts a site"); products appear only as the subjects of cited cases.

## 3. Prerequisites, promises and pre-training

**From earlier chapters (reuse the glossary wording verbatim):** Delegation Ladder, agency, agent (Ch. 5, Ch. 3); task-tool fit, fit matrix, data terms, data class, data gate (Ch. 12); sandbox, least privilege, development vs. production, dry run, done-criteria, test inputs, planted fault (Ch. 14); data-flow map, trust boundary, prompt injection, Risk Heat Map, risk register, risk owner, mitigation, canary, attack surface, the CIA triad, the attack families (Ch. 15, including 15.7); ownership (of a text), deployer, license (Ch. 10, 18); independent check (Ch. 8); prototype (Ch. 19).

**Pre-training card: "Words for builds" (Core, ~150 words, placed just before B.1, with FB.2).** These are the only technical words a reader needs before B.1. Each gets one plain sentence:
1. **code** -- the written instructions a computer follows;
2. **app or site** -- code that people use through a screen;
3. **server** -- a computer elsewhere that runs part of a build for its users;
4. **database** -- where a build keeps what people enter;
5. **hosting** -- renting a place on the internet for a build to run;
6. **public key** -- a code that tells a service which project is calling; it is made to sit in page code, and it is safe only if access rules stand behind it;
7. **secret key** -- a code that works on its own (it reads private data, spends money, or acts as an administrator), so it must never be in page code, a shared file or a message;
8. **sign-in (authentication)** -- checking who someone is;
9. **permission (authorization)** -- checking what that person may do;
10. **access rule** -- a setting at the service that says who may read or change which data;
11. **package** -- ready-made code a build borrows (a dependency);
12. **public link** -- an address that lets anyone who has it open a file or page.

"Test copy" (Ch. 14: development vs. production) is recalled on the same card. **FB.2** shows the parts in two small pictures: a web form (the visitor's browser and page code -> server and database, with an access rule; a public key and a secret key marked) and a spreadsheet automation (sheet -> script -> email service, with the account it runs under).

| # | Misconception | Where confronted | Refutation check (must not create) |
|---|---|---|---|
| M1 | "If it runs and the demo works, it is finished and safe." | B.1 introduced; B.4: a working page can still let anyone read the database (CB-1). Perry et al. (2023): participants with an AI assistant wrote less secure code **and** were more likely to believe it was secure. Pearce et al. (2022): about 40% of 1,689 programs generated for 89 scenarios contained a weakness from a list of common ones | "Generated code is always insecure": most of Pearce's programs had none of the tested weaknesses. The point is that running is not evidence of safety |
| M2 | "I cannot read code, so checking it is not my job" -- or its twin, "I must learn programming before I can build anything." | B.4: reading for **behavior** (what comes in, where it goes, who may do what, what it reaches out to), plain-word searches, tests | "Anyone can audit code after one chapter": B.4 and B.7 say plainly which checks need a professional |

| M4 | "Nobody will find my small build, and a key in my code is hidden." | B.4 and B.5: every visitor's browser downloads the page code, so anything in it is public. ## 5. Concept sequence

**Session question, answered in the Summary:** *When an AI tool can build working software for you, what is still yours to do before anyone else relies on it?* Hedged answer, in seven steps. Decide whether a build is the right answer at all (an existing tool may fit better). Brief the tool so it knows the reach, the data and what it must never do. Own the decisions it cannot make: what data the build collects, who can reach it, where it runs, which keys it holds and who answers for it. Read it for behavior and test it with real effects switched off. Treat the tool's own account as a lead, and remember that a test through the page can show a leak but cannot prove there is none. Look for the six weak spots that generated software often has. Re-rate the risk as the reach grows, because on the internet "who can reach it" becomes "anyone". Finally, stop, step down or bring in a professional when the build touches protected data, money or other people's accounts; when people rely on it who did not choose it; or when it has a part, or an access rule, you cannot explain.

**Attribution tiers for the main case (Moltbook, CB-1): confirmed, reported, inferred.**

| Tier | Statement | Source |
|---|---|---|
| Confirmed (the researchers' own technical record) | The site's page code held a **public ("publishable") key** for its hosted database service, of the kind that service designs to be exposed in page code. **The database had no access rules (row-level security) in place**, so that public key gave anyone read and write access. The failure is the missing access rules, not the presence of the key. Exposed: about 1.5 million API authentication tokens for the site's agents; about 35,000 email addresses; 4,060 private conversations between agents, some holding plaintext keys to other services (real secrets). Write access was confirmed by a test edit. After a report by direct message, the site's team fixed the tables in several steps on Jan 31-Feb 1, 2026 (about 23:29-01:00 UTC). ## 9. Application Assignment -- AB Build Review (draft)

*(O6 - LO5, LO3, LO2; LO6, LO4 and LO7 secondary - Create.)* Started in Lab B.1 (section B.8). Due when your instructor sets it, or, for self-learners, when you choose. Expect about 5 minutes before the lab and **about 45 minutes after it on the packet route** (about 30 if you reuse your lab drafts; about 60 on the own-build route). **No programming and no AI tool are required.**

**Two routes, same rubric.** The **packet route** is the default: a provided build packet; packet 1 is in the public companion files, and packets 2-3 are in the instructor package. The **own-build route** is a stretch: a small build you obtain with a tool your institution provides or approves, kept on your own device or in a sandbox.

**Safety rules for the whole assignment (printed in a box):** do not publish anything; run any build only on your own device or in a sandbox, on a test copy; use no personal, confidential or restricted data (12.5); never paste a real password or secret key into a tool or a file -- use a clearly fake one (a canary, 15.6); switch off or simulate every send, publish, pay and delete; read before you run (Lab B.2 order); if a tool asks to install something, stop and record the request instead.

**What to submit:**

1. **Brief:** on the packet route, critique the packet's brief and rewrite three parts; on the own-build route, write your brief. Either way: purpose, users, reach, data in and its class, at least three never-do rules (one about keys), two or three done-criteria (one about access, saying how it is checked), and the request for a list of services, keys (public or secret) and packages. Note one revision.
2. **Responsibility map:** each decision area (data, access, place and account, keys and costs, updates and patching, take-down), marked AI-produced / decided by you / verified by you (how) / provided by a service.
3. **Reading pass and tests:** the four questions answered for each file or setting. Packet route: interpret the three recorded runs and specify one more you would run. Own-build route: three runs with real effects off (typical, edge, one planted fault). For each run, say what it shows and what it cannot show (e.g., "the signed-out test found no leak through the page; the access rule at the service was read: it says ...").
4. **Six-weak-spot check:** for each weak spot, found / not found / cannot tell, with the evidence and its tier (documented by your test, your reading or a source; inferred by your reasoning).
5. **Heat map:** one risk rated at the build's current reach and at internet reach, with documented/inferred marks; a mitigation with an owner for anything in the high-impact band; both rows written as register rows (15.5-15.6).
6. **Stop decision and handover:** which stop-list items apply; which of the five outcomes you choose; if you would bring in a professional, who it would be and what you would hand over.
7. **Defense for a non-specialist (80-100 words):** in plain words, why your build may or may not reach the people you planned.
8. **AI Use Declaration:** tools, purpose, what you accepted, rejected or revised, how you verified it, and where your own judgment shaped the work (or "no AI tools used").

Valid full-mark results: "do not build; an existing tool fits", "keep it local", "bring in a professional before anyone else uses it". Tool-specific steps are in Compass, never click paths in the book.

## 15. Risks and checks

- **Named companies and a named founder (CB-1, CB-2, Base44):** every statement is tiered; the founder is referred to by role in running text; no claim that AI caused a failure goes beyond what a primary record shows (B-D3). The Lovable responsibility dispute is described, not resolved.
- **Public vs. secret keys:** no sentence may call a public key itself the leak. The reviewer checklist checks every case paragraph, figure and AB packet against R1.
- **What tests prove:** no sentence may say that a page test shows the data is closed (R2).
- **Security how-to risk:** the chapter must not become an attack guide. No exploit steps, no queries, no tool names for scanning other people's systems; the "direct test of the service" is named only as a professional's job on the builder's own build. The Mini-Project forbids probing systems the student does not own, and the lab uses printed packets.
- **Scope creep into a programming or web-development tutorial:** fragments of <= 12 lines, annotated in English, never written by students; no framework, language or hosting platform taught; at least half the worked and faded examples are non-web builds; a reviewer checklist item for the pedagogy review.
- **Two taxonomies:** "family" is used only for 15.7's attack families; Chapter B uses "weak spot" throughout, with the mapping table as the bridge.
- **Scope creep into health:** no clinical build, no patient data, Marcus not featured (D31).
- **Vendor statistics:** GitGuardian, Truffle and Veracode sell detection tools. Label each "company report", keep their exact wording, and keep GitGuardian and Veracode to Deep B.A.
- **Ageing:** platform behavior, case statuses, the OWASP edition, the 15.7 family list and tool capabilities go to the refresh list with "as of" dates.
