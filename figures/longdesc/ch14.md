## Long descriptions

### F14.2 (f14-02-storyboard)

Seven boxes left to right, each with a date above: Early July, app built with the agent, posts daily (dashed, reported); Jul 17, post saying the day before was full of deceit, fake data alleged (dashed); By Jul 18, freeze: told not to change anything without permission (dashed); Jul 18, database deleted during the freeze (thick risk border, dashed: reported); Agent's text, a hexagon saying the rollback cannot restore the data (dashed); Jul 19, the user says the rollback worked (dashed); Jul 20, the CEO's post saying dev/prod separation is rolling out (solid, verified fill: read by the book). Below: a solid box, Dec 17, 2025 company blog, the agent gets only the development database, noting the post does not mention the incident; a dashed box, what limited the harm: a restore point the agent said would not work. Legend: solid = company record read; dashed = reported; thick = the harm; hexagon = text the agent produced.

### F14.3 (f14-03-four-kinds)

An arrow across the top labeled 'Who fixes the next step?'. Below it four shapes: Chat assistant (rounded; you, each turn; you run each step), Prompt chain (rounded; you, in advance; you run each step), Automated workflow (rectangle; people, in advance; software runs each step), Agent (hexagon; the model, as it goes; software runs each step). A shaded box beneath says what it can change (read, write, send, pay) is a separate permissions question; an approval gate limits that without changing the kind of system. A note says agency is a way of working, not a kind of system.

### F14.4 (f14-04-agent-loop)

Signature 9. Top row left to right: Goal (rounded, a person sets it) → Plan (hexagon, the model proposes the next action) → Approval gate (diamond, a person) → yes → Tool call (rectangle, the system runs it). A curved arrow from the gate back to Plan is labeled 'no, or edited: a new plan'. From Tool call an arrow goes down to Observation (rectangle, the result enters the context window) → Check point (rounded, a person inspects a result) → Stop? (diamond). From Stop?, 'yes' leads left to Hand back (rounded, to a person); 'no: next pass' leads up to Plan. A wide strip at the bottom: Log, the system records every plan, tool call, observation, approval and stop, with times. Legend: hexagon = AI; rectangle = the system runs it; diamond = a decision; rounded = a person. With gate="soft", the gate is a hatched risk diamond labeled 'Soft gate: an instruction (may be skipped)', and the legend adds 'hatched = a soft gate'.

### F14.5 (f14-05-sam-trace)

The agent loop of Figure 14.4 with the approval gate highlighted and notes: beside Plan, passes 1–7: search, four datasheets, cart, draft; beside the gate, pass 8: 'place order, $312' → treasurer + second officer; beside Observation, pass 6: cart total $312; beside Stop?, stop points: over budget line; part not on the list; more than 15 passes. Footnote: Sam's current design (constructed); the gate is there because of the test that went wrong in section 14.5.

### F14.6 (f14-06-compounding)

Line chart, x axis number of steps 1–30, y axis runs with no error at all (%). Three falling curves computed as p to the power n: all solid lines told apart by marker shape and a direct label at the line's end: 99% per step (circles) ends near 74% at 30 steps, labeled 82% at 20 steps; 95% per step (squares) labeled 36% at 20 steps; 90% per step (open triangles) labeled 35% at 10 steps and falling to about 4% at 30. Source note: this book's calculation; assumes independent steps; not data about any agent; real errors can be correlated (worse) or harmless and fixed (better).

### F14.7 (f14-07-where-people)

Two-by-two grid. Columns: who would bear an error, only you or other people. Rows: can be undone, cannot easily be undone. Cells: undo yes and only you, review the log afterward (a draft, a cart, a test copy); undo yes and others, check point before others see it (a shared draft, a calendar hold); undo no and only you, approval gate or keep the step (deleting your own files); undo no and others, approval gate before it takes effect (send, publish, pay, delete shared data), drawn thick. Notes: read-only actions change nothing, log them; stop points apply in every cell; the cells are this book's arrangement, not a rule.

### F14.8 (f14-08-gates-sim)

Two panels from this book's simulation (20 steps, 95% per step). Left bars, runs ending in the final irreversible action on a wrong result: no person 64%, one gate before the final action 19%, check points every 5 steps plus the gate 6%, at an 80% catch rate; open markers at a 50% catch rate: 41% and 22%. Right paired bars per run: steps redone 8.2 and checks by a person 1.8 for one gate; steps redone 3.8 and checks 5.1 for checks plus gate. Source note lists the assumptions: independent steps and misses, no false alarms, no approval fatigue, only the final action irreversible; not data about any agent.

### F14.9 (f14-09-people-points)

The agent loop of Figure 14.4 with three parts highlighted and labeled: approval gate, approve before an action takes effect; check point, inspect a result before later steps build on it; stop?, halt and hand back when a condition is met.

### F14.10 (f14-10-soft-hard)

Two columns separated by a thin line. Soft gate: an instruction 'always ask before ordering' → it becomes text in the context window → the model produces the next action (hexagon) → action may run without asking (thick risk border). Hard gate: the model proposes an action (hexagon) → the system pauses: the tool cannot run yet → a named person approves, edits or rejects (thick rounded) → only then does the action run (verified). Note: soft-gate examples in this chapter are the code freeze and Operator's confirmation step.

### F14.11 (f14-11-ladder-gate)

Signature 7, the Delegation Ladder, with the agency rung highlighted and the note 'an approval gate: a person sees each consequential action first'; footnote: the gate restores a check at the agency rung; the rung does not change (Chapter 5).

### F14.12 (f14-12-permissions)

Three tool boxes with their permissions as text: band calendar, read yes, write no, send no, pay no; drafts folder, read yes, write drafts only, send no, pay no; band mailing list, send reminders only after his weekly approval, pay no. A thick bottom box: never touches his email account, anything from his nursing placement, any payment or room booking.

### F14.13 (f14-13-log-report)

Left column, the log written by the system: four boxes, time of each pass; plan text and tool call; observation returned; who approved and when. Right column, the agent's report, a large hexagon: more text, predicted from the context window, fluent and possibly wrong; in the Opening Case it said the rollback would not work and the user later said it did. Notes: read the log to learn what happened and treat the summary as a claim to check (Chapter 8); a log shows what was done, not why the model produced it (Chapter 17).

### F14.14 (f14-14-lucia-review)

Flow: AI draft of a reply (hexagon) → diamond 'refund, discount or account change?' → yes, up to an approval queue where a support team member approves (thick) → no, right to 'sent and logged' → weekly sample of 20 sent replies → diamond 'policy error found?' → yes → pause automatic sending for that category (thick risk). Note: Lucía's proposal, constructed, no customer data.

### F14.15 (f14-15-dry-run)

Process: test inputs, typical and edge, and one planted fault (risk fill: wrong result, missing data or hidden instruction) → side effects off, run on paper or in a test copy → record each step (right? checked how?) → diamond 'fault caught?' → yes: keep the design; no: move or add a point, narrow a permission, or use a simpler system. Note: then rerun the run that failed; one run is a sample.

### F14.18 (f14-18-chain-c11)

### F14.19 (f14-19-gate-leans)

Draft reply produced by the model (hexagon) → a doctor edits every draft (dashed rounded = inferred, the authors' suggestion of anchoring; subtitle 'edited replies resembled the drafts', a measured result) → reply that would be sent. Notes: the gate existed; the authors suggest anchoring and automation bias; Chen et al. (2024), six radiation oncologists, simulated messages, GPT-4 drafts, 2023.

### F14.21 (f14-21-five-roles)

Five stacked rounded boxes, each indented further: 1 operator, you direct and the agent helps when asked; 2 collaborator; 3 consultant, the agent leads and asks you for direction; 4 approver (thick, highlighted), the agent acts and you sign off on consequential actions; 5 observer, the agent acts and you watch the log and can switch it off. An arrow down the right: more autonomy. Source: paraphrased from Feng, McDonald and Zhang (2025).
